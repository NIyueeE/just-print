# v0.3.13

代码审阅修复版：审阅前后端时发现三个「只在特定路径出现、但一出现就很疼」的界面
缺陷——关闭上传错误提示会丢掉已经转换好的文档、CUPS 卡住时刚打完的任务从列表里
消失、登出间隙轮询还在用空令牌撞 401。另有一个客户端与服务端白名单不一致的小问题。
前端测试 55 → 58（新增 3 个回归用例），后端无改动。无损升级。

## 🐛 修复

- **关闭上传错误提示会丢掉已经转换好的文档**：上传区错误提示的「×」此前派发
  `upload/select`，而该 action 会用 `emptyUpload()` 重建整个上传状态。于是第二次
  上传失败（超时、503）时，第一次已经转换好的 PDF、预览和服务端文件引用被一并
  清空——服务端那个文件还有 30 分钟 TTL、完全有效，用户却不得不重新上传一遍。
  现在改用专用的 `upload/error-dismiss`：只清除错误文案，并按屏幕上实际所处的
  阶段回到 `ready`（已有转换结果）或 `selected`（仅选了文件）。
- **CUPS 卡住时刚打完的任务从列表消失**：`pruneJobs` 只对列表总量设了
  `MAX_JOB_VIEWS`（50）上限，进行中的任务却没有独立上限。打印机脱机、缺纸或驱动
  挂起时任务会一直停在 `queued`/`printing`，active 逐渐占满整个预算，
  `MAX_JOB_VIEWS - active.length` 把已结束任务裁成 0——用户刚打完的任务从列表里
  消失，卡住的旧任务却一直占着版面。新增 `MAX_ACTIVE_JOB_VIEWS`（20）作为进行中
  任务的独立上限，剩下的位置固定留给已结束任务。
- **登出间隙轮询用空令牌撞 401**：任务轮询的启用条件只有 `hasActive`，没有检查
  令牌。退出登录时视图是异步清空的，这个间隙里轮询仍可能发出一次带空 Bearer 令牌
  的请求，之后每个周期都撞一次 401（并触发一次登录态复位）。现在与打印机轮询
  一致，用 `state.token !== ''` 一并守住。
- **客户端放行服务端会拒绝的 `.log`**：前端的文本类扩展名集合包含 `log`，但后端
  `SUPPORTED_EXTENSIONS` 白名单里没有它——客户端预校验放过、整个文件上传完成后才
  被服务端以 `415` 拒绝，白跑一趟。已从集合中移除（其余 65 个扩展名均与后端一致）。

## 🧪 测试与验证

- 前端新增 3 个「先红后绿」回归用例（55 → 58）：
  - `dismissing an error keeps an already converted document`：已有转换结果时
    关闭错误提示，`result` / `previewUrl` / `file` 必须保留、阶段回到 `ready`；
  - `dismissing an error without a result returns to the selection step`：无结果
    时回到 `selected`，不会卡在 `error` 阶段；
  - `keeps finished jobs visible when active jobs pile up`：塞满 `MAX_JOB_VIEWS`
    个进行中任务后，已结束任务必须仍在列表内，且进行中被截断到
    `MAX_ACTIVE_JOB_VIEWS`。
- `tsc -b`、ESLint、Prettier、Vitest（58 个）、`vite build` 全部通过；后端未改动，
  仍整套跑通 `cargo fmt --check`、`cargo clippy --all-targets --all-features -D warnings`、
  `cargo test --all-features`（61 个）与入口脚本断言。
- 冒烟（真实镜像 + CUPS-PDF 端到端）：健康检查、就绪、上传 → 预览 → Markdown 排版
  → 打印到完成、幂等重放、任务取消、文件删除全通过。

## 升级说明

直接替换镜像即可，客户端无需改动：接口路径、请求/响应结构与错误码均未变，
三个修复都只影响前端界面状态与列表裁剪逻辑。`.log` 文件请改用 `.txt` 上传
（或打包为受支持的格式）。
