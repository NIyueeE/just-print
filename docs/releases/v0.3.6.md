# v0.3.6

修掉一个「界面上选了、实际被 CUPS 悄悄丢掉」的真 bug：**分辨率从来没有按选择生效过**。

## 🐛 修复

- **分辨率选项静默失效**：CUPS 在 PPD 队列上把 job 属性交给 `cupsMarkOptions()`
  去打标 PPD，而它只用取值去匹配 PPD choice 名（通常是 `600dpi`）；cupsd 自己把
  IPP 分辨率序列化成的却是 `600x600dpi`，两者对不上，标准属性 `printer-resolution`
  被静默忽略，分辨率**退回 PPD 默认值**——界面上选 1200dpi，`gs` 实际收到的是
  `-r600x600`（`/var/log/cups/error_log` 里可直接看到）。
  现在后端在标准属性之外附带一个 PPD 风格的同值属性 `Resolution=<N>dpi`
  （`src/cups/options.rs`）：PPD 队列凭 choice 名生效，其它队列按未知属性忽略
  （CUPS 默认 `ipp-attribute-fidelity=false`，不会因此拒绝任务）。
- 影响范围：所有走 PPD 过滤链的队列（USB / 通用 PCL / HPLIP 等，包括
  `pxlmono.ppd`、`generpcl.ppd`）；IPP Everywhere 队列由 CUPS 直接转发标准属性，
  本来就不受影响。
- 双面（`sides`）没有这个问题：CUPS 在 `job.c` 与 `cupsMarkOptions()` 两处都做了
  `sides` → `Duplex` 的映射，取值也是 IPP 关键字，因此一直正常。

## 🔍 为什么现在才发现

老实现（≤ v0.2.5）的选项目录来自 `lpoptions -l`（PPD 名/choice 名），提交时用
`lp -o Resolution=600dpi`，正好是 CUPS 认的那条路，所以一直是对的；v0.3.0 换成
标准 IPP 属性名（`printer-resolution=600x600dpi`）之后才落进这个坑——标准属性
反而不如 PPD 名好使。

## 🧪 测试

- 新增单测 `adds_ppd_resolution_alias_for_cups_queues`：覆盖 `600dpi`、
  `600x1200dpi`、`47dpcm` 三种取值到 PPD 风格属性的映射；后端测试 32 → 33。

## ✅ 验证

- `just check` 全绿：后端 33 个测试、前端 44 个测试、入口脚本 24 项断言。
- 本机用真实 CUPS 队列（`pxlmono.ppd` + `OptionDuplex=True`）跑通整条链后对比：
  修复前 `gs … -dDuplex -r600x600`、PCL-XL 头 `@PJL SET RESOLUTION=600`；
  修复后 `-r1200x1200`、`@PJL SET RESOLUTION=1200`，双面属性不变。

## 使用提示

- 排查分辨率是否真的生效（容器内）：

  ```bash
  grep 'Ghostscript command line' /var/log/cups/error_log | tail -1
  # 或直接看 PCL-XL 头：@PJL SET RESOLUTION=1200
  ```

- 改了 `JUST_PRINT_USB_PPD` 之后队列不会自动换驱动：入口脚本对**已存在的同名队列**
  只更新 `JUST_PRINT_USB_OPTIONS`，要换 PPD 请先 `lpadmin -x <队列名>` 或重建容器。
